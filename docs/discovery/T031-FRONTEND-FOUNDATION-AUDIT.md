## 3. Architecture conflicts

**No hard conflicts found** between the existing code and the target architecture proposed in T031.01 — the existing foundation doesn't preclude or contradict anything proposed there; it simply hasn't reached most of it yet.

**One genuine, evidence-based compatibility constraint, not a conflict but worth flagging as binding going forward:** `components.json`'s `style: "base-nova"` commits this project to `@base-ui/react`'s `render`-prop composition API (confirmed in active use in both existing `ui/` primitives and their one consumer, `theme-toggle.tsx`) rather than the classic Radix `asChild` pattern most shadcn tutorials/examples assume. Any future SPEC or component work that assumes Radix-style composition (a common default assumption) would be working against what's actually installed and already working here — this needs to be an explicit, conscious choice in SPEC-T031, not an accidental mismatch discovered later.

## 6. Dependency cleanup

**No dead/unused dependencies found.** Every package in `package.json` maps to either (a) active current use (`next`, `react`, `react-dom`, `next-themes`, `@tanstack/react-query`, Tailwind/shadcn deps) or (b) a deliberately pre-installed, approved-but-not-yet-wired-in future need per the requested tech stack (`axios`, `react-hook-form`, `@hookform/resolvers`, `zod`, `zustand`) — none of these are accidental cruft; they match T031.01's explicitly authorized stack list item-for-item.

Low-impact (doesn't break anything, only affects production-bundle-relevant dependency auditing precision later).

## 8. Implementation impact

- Deleting the 5 `public/` SVGs: **zero impact** — confirmed nothing imports them.
- Extending `lib/api.ts` in place: **zero impact on other files** — it's currently imported by nothing (§`lib/api.ts` row), so completing it cannot break any existing consumer; it only starts becoming consumable once something imports it.
- Adding an `AuthProvider` to `providers/index.tsx`'s composition chain: **zero impact on `layout.tsx`** — `layout.tsx` only imports `<Providers>` as an opaque wrapper and never reaches into its internals, so `providers/index.tsx` can gain new children in its composition without `layout.tsx` needing any change.
- Replacing `page.tsx`: **impacts nothing else** — it's a leaf route file; only `theme-toggle.tsx` is imported by it, and that import can simply move to wherever the new landing/redirect content lives.
- Rewriting `package.json` scripts: **zero runtime impact** — purely tooling, doesn't touch any imported module graph.

No file audited here has enough current inbound dependents to make any of the proposed changes structurally risky — the shallow current import graph (confirmed by direct tracing, not assumed) is itself a favorable finding for how cheaply this foundation can be extended.
