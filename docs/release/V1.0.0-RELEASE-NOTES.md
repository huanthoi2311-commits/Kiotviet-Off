# POS ERP Enterprise — v1.0.0 Release Notes

**Status khi tài liệu này được soạn: V1.0 READY FOR RELEASE (chưa gắn tag, chưa publish GitHub Release).** Xem `PROJECT_STATUS.md` để biết trạng thái xác nhận mới nhất trước khi coi tài liệu này là đã phát hành chính thức.

---

## 1. Phạm vi sản phẩm (Product scope)

POS ERP Enterprise v1.0 là hệ thống quản lý bán hàng/kho/mua hàng **offline, 1 máy tính** (không LAN/mobile/PWA ở V1), đóng gói qua Docker Compose cho Windows. Phạm vi nghiệp vụ cốt lõi:

- **Master Data**: Product/Category/Brand/Unit/Barcode, Customer, Supplier, Warehouse/Branch.
- **Purchase**: Purchase Order (tạo → Duyệt → Xác nhận nhận hàng), Purchase Return.
- **Inventory**: Transfer (giữa kho), Stock Count, Inventory Adjustment — mọi transition trọng yếu dùng optimistic-lock (CAS).
- **POS / Checkout**: giỏ hàng, thanh toán, Invoice, Payment — có Idempotency-Key chống double-submit.
- **Sales Return**: tạo → Gửi duyệt → Duyệt → Xác nhận nhận hàng → Hoàn tất, hoàn tồn kho đúng 1 lần.
- **Customer / Supplier**: quản lý thực thể, Customer Point (đọc), Supplier Debt (đọc).
- **Reports**: Purchase Report (theo Supplier/Product/Tháng), export Excel/CSV/PDF.
- **RBAC**: Role/Permission theo tổ chức, Platform Admin riêng biệt.

## 2. Purchase

Luồng nhập hàng đầy đủ: tạo Purchase Order (chọn Chi nhánh/Nhà cung cấp/Sản phẩm/Kho nhận/Số lượng/Đơn giá) → Duyệt → Xác nhận nhận hàng (cộng tồn kho đúng 1 lần, có CAS chống double-submit) → Purchase Return khi cần trả hàng nhà cung cấp. Purchase Report tổng hợp theo Supplier/Product/Tháng, xuất Excel/CSV/PDF.

## 3. Inventory

Transfer (chuyển kho), Stock Count (kiểm kê), Inventory Adjustment (điều chỉnh) — mọi transition hoàn tất (`.complete()`) đều qua optimistic-lock, chống 2 request đồng thời cùng áp dụng 2 lần. Tồn kho phản ánh chính xác qua toàn bộ vòng đời Purchase → Sales → Return, đã chứng minh bằng phương trình đầu-cuối thật (real-browser E2E, xem mục 11).

## 4. POS/Checkout

Giỏ hàng → chọn Chi nhánh/Kho xuất/Phương thức thanh toán → Thanh toán → Invoice + Payment. `Idempotency-Key` đảm bảo double-click/double-submit không tạo 2 Invoice — request lặp lại nhận đúng invoice cũ (replay), không tạo giao dịch mới.

## 5. Sales Return

Tạo phiếu trả hàng từ Invoice → vòng đời đầy đủ Gửi duyệt → Duyệt → Xác nhận nhận hàng (cộng tồn kho đúng 1 lần, transition duy nhất có hiệu ứng tồn kho) → Hoàn tất (không đổi tồn kho thêm).

## 6. Customer/Supplier

Quản lý thực thể Customer/Supplier đầy đủ CRUD + Archive/Restore. Customer Point và Supplier Debt hiện ở mức đọc (xem mục Known Deferred Items cho phần mutation UI).

## 7. Reports

Purchase Report (nhóm theo Supplier/Product/Tháng, khoảng ngày tuỳ chọn, xuất Excel/CSV/PDF). Timezone của khoảng ngày là **browser-local** (không phải Organization/Branch timezone — các field đó hiện chưa được dùng ở tầng nghiệp vụ) — xem mục Known Deferred Items.

## 8. Security hardening

- **RBAC tenant isolation**: mọi truy vấn nghiệp vụ được lọc theo `organizationId` của actor ở tầng service (Checkout/PurchaseOrder/Transfer/StockCount/InventoryAdjustment đã xác nhận qua audit T051.00/T051.06A/T051.06B, tái xác nhận ở T051.09) — StockCount đọc thực thể tổ chức khác trả về 404 (không phải 403), không rò rỉ sự tồn tại.
- **Auth**: JWT access token (Bearer) + refresh token thật (httpOnly cookie, `Secure` theo `AUTH_COOKIE_SECURE`, `SameSite=Lax`, `Path=/`), rotation-on-every-use, throttle trên `/auth/login` (5/60s) và `/auth/refresh` (20/60s).
- **CORS**: whitelist origin tường minh, từ chối `*`.
- **Redis**: không map cổng ra host trong cấu hình production đóng gói (chỉ nội bộ mạng Compose).
- **Branch protection**: `main` được bảo vệ qua GitHub Repository Ruleset — PR bắt buộc, required status checks (Backend/Frontend), chặn force-push, chặn xoá branch, admin chỉ bypass qua pull_request (không push trực tiếp).
- **Không log token thật** ở bất kỳ đâu trong backend.

## 9. Concurrency hardening

Optimistic-lock (CAS, cột `version`) trên mọi transition hoàn tất trọng yếu: `PurchaseOrder.receive`, `PurchaseReturn.complete`, `Transfer` transitions, `StockCount.complete`, `InventoryAdjustment.complete`. Checkout dùng cơ chế Idempotency-Key 2-transaction (Reserve tách khỏi Business Transaction), chịu được crash/timeout thật — đã chứng minh qua double-click thật trên trình duyệt thật (real-browser E2E): đúng 1 Invoice, đúng 1 Payment.

## 10. Backup/Restore

`pg_dump`/`pg_restore` thật, xác minh bằng `pg_restore --list` + restore vào database cô lập + so sánh row-count nguồn/đích. Chạy qua `docker compose exec` (đúng đường vận hành viên Windows sẽ dùng) — đã chứng minh thật trong CI trên nhiều lần chạy, kể cả trên chính merge commit cuối cùng của mỗi package release-hardening.

## 11. Windows deployment

`docker compose build` → `bring-up` (migrations → permission bootstrap → first-admin bootstrap, tự vá companion Organization Settings/Subscription nếu thiếu ở lần chạy sau) → Postgres/Redis/backend/frontend → health check → sẵn sàng đăng nhập. Drill khởi động lại (backend/Postgres/toàn stack) xác nhận dữ liệu bền vững qua named volume. Runbook đầy đủ: `docs/release/WINDOWS-DEPLOYMENT-RUNBOOK.md`.

## 12. Real-browser verification

Bộ Playwright tối thiểu (`T051.08`) chạy trên stack đóng gói thật (frontend/backend/Postgres/Redis containers thật, không mock network): đăng nhập UI thật → Purchase Order → Duyệt → Nhận hàng → POS Checkout → Invoice → Sales Return đầy đủ vòng đời → double-click idempotency → tenant smoke — 7/7 test, xác nhận qua log CI trên chính merge commit (không chỉ trạng thái tổng hợp).

## 13. Known deferred items

Xem mục riêng bên dưới ("Known V1 Deferred Items") — các UI quản trị/nâng cao **chủ đích chưa triển khai ở V1**, không phải thiếu sót/lỗi.

## Known V1 Deferred Items

Các mục sau **chủ đích chưa triển khai ở V1** (không phải bug) — tái xác nhận còn chính xác tại T051.09:

- Supplier Import UI
- Supplier Payment UI — **kèm điều kiện**: đã xác nhận 1 race condition thật (tái hiện trên Postgres thật) ở tầng backend cho SupplierPayment, hiện KHÔNG có đường tiếp cận từ UI V1 (không phải RC blocker). Phải sửa TRƯỚC KHI Supplier Payment UI được triển khai, không sớm hơn — ghi chú này phải theo bất kỳ RFC/SPEC tương lai nào cho tính năng đó.
- Customer Point manual mutations (hiện chỉ đọc)
- RBAC management UI (Role/Permission hiện chỉ có API, không có màn hình quản trị)
- Discount admin UI
- Organization Settings UI
- Multi-branch management UI
- Advanced/thêm báo cáo ngoài Purchase Report
- TLS packaging (đóng gói V1 dùng HTTP nội bộ, vận hành viên tự cấu hình TLS ở tầng reverse-proxy nếu cần)
- Backup encryption at rest
- Custom Windows service (hiện chạy qua Docker Desktop, không đóng gói thành Windows Service riêng)

### Technical debt đã ghi nhận (không phải bug, cần quyết định tương lai)

- **Report timezone**: khoảng ngày của Purchase Report dùng browser-local timezone (quyết định tường minh cho mô hình 1-máy-tính offline V1) — `Organization.timezone`/`Branch.timezone` tồn tại trong schema nhưng chưa được dùng ở tầng nghiệp vụ. Cần quyết định lại trước khi triển khai mô hình nhiều điểm bán/tập trung hoá.
- **SupplierPayment concurrency risk**: xem mục Supplier Payment UI ở trên — race latent, chỉ ở tầng backend, không có đường tiếp cận thật ở V1.
